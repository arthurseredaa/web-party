# web-party-game — Roadmap

Настільна гра (свій унікальний сетинг): ноутбук — спільний екран з полем, телефони — геймпади.

**Мета навчання:** realtime / WebSockets, архітектура бекенду, бази даних глибше, TypeScript усюди.

**Як користуватися цим файлом:** один етап за раз. Етап закрито, коли всі пункти «Готово, коли…»
відмічені. Питання собі — відповісти своїми словами (можна прямо тут, під питанням), перш ніж іти далі.
Документацію читати точково під поточну тему, а не курс від початку до кінця.

---

## Етап 1 — Монорепо і TypeScript-сетап

**Вчу:** pnpm workspaces, `tsconfig` (base + per-package), як пакети імпортують один одного.

Структура:

```
apps/server       Node + TS + Express + Socket.IO
apps/screen       React + Vite — екран на ноуті
apps/gamepad      React + Vite — геймпад на телефоні
packages/shared   спільні типи повідомлень + zod-схеми
```

Готово, коли…

- [x] `pnpm install` в корені ставить залежності для всіх пакетів
- [x] `server`, `screen`, `gamepad` імпортують щось із `shared`, і типи працюють в IDE
- [x] одна команда в корені запускає все разом у dev-режимі
- [x] `tsc --noEmit` проходить у всіх пакетах

Питання собі:

- Навіщо `shared` окремим пакетом, а не просто папка, з якої всі імпортують відносним шляхом?
- Чим відрізняється `tsx`/`ts-node` у dev від збірки через `tsc` для продакшену?

## Етап 2 — Кімнати і лобі (перше «вау»)

**Вчу:** Socket.IO поверх Express: події й acknowledgements, rooms, життєвий цикл з'єднання, broadcast.

- Екран створює кімнату → сервер повертає короткий код (типу `ABCD`)
- Екран показує код + QR-код з посиланням на `gamepad`
- Телефон вводить ім'я, заходить у кімнату
- На екрані наживо з'являється список гравців

Готово, коли…

- [ ] телефон у тій самій Wi-Fi заходить у кімнату через QR (Vite `--host`, IP ноута)
- [ ] 2+ телефони в одній кімнаті, екран бачить усіх
- [ ] натиснув кнопку на телефоні → щось змінилось на екрані
- [ ] гравець закрив вкладку → зник зі списку

Питання собі:

- Чим WebSocket відрізняється від HTTP-запиту? Чому тут не підходить polling?
- Де зараз живе стан кімнати? Що з ним станеться, якщо сервер перезапуститься?
- Як сервер розуміє, яке з'єднання належить якій кімнаті? Що тут дає Socket.IO rooms, а що довелося б робити руками на голому `ws`?

## Етап 3 — Протокол, валідація, надійність

**Вчу:** типізовані мапи подій Socket.IO, zod, middleware, обробка помилок, reconnect і ідентичність гравця.

- Усі події описані в `shared`: `ClientToServerEvents` / `ServerToClientEvents` + zod-схеми для payload'ів
- Сервер валідує payload кожної вхідної події zod'ом, на невалідне — відповідає помилкою (ack), а не падає
- Heartbeat (ping/pong) у Socket.IO вже вбудований: подивитися, як він працює і які в нього таймаути
- Reconnect: гравець отримує токен при вході (перевіряється в middleware підключення); телефон
  заблокувався і повернувся → той самий гравець, а не новий. Socket.IO перепідключає сокет, а
  не гравця — ця частина твоя

Готово, коли…

- [ ] змінив тип події в `shared` → TS підсвічує помилки і на сервері, і на клієнтах
- [ ] сміття в payload (не той тип полів, відсутні поля) не валить сервер
- [ ] заблокував телефон на хвилину, розблокував → повернувся у гру тим самим гравцем
- [ ] вимкнув Wi-Fi на телефоні → через кілька секунд сервер позначає гравця як offline

Питання собі:

- Чому довіряти повідомленням від клієнта не можна, навіть якщо клієнт — «мій» код?
- Як відрізнити «гравець вийшов» від «у гравця мигнув інтернет»?
- Що Socket.IO відновлює сам після розриву, а що ні?

## Етап 4 — Ігрова логіка як машина станів

**Вчу:** state machine, server-authoritative архітектура, чисті функції, тести на Vitest.

- Фази: `lobby → turn_start → rolling → moving → (minigame) → round_end → game_over`
- Уся логіка — чисті функції: `(state, action) => newState`, без сокетів і БД усередині
- Телефон надсилає **намір** («кидаю кубик»), сервер вирішує, чи можна, і розсилає новий стан
- Поле: клітинки (монетки +/−, пастки), рух фішки, порядок ходів

Готово, коли…

- [ ] можна зіграти повну партію на N раундів від лобі до переможця
- [ ] гравець не може ходити не у свій хід (сервер відхиляє)
- [ ] ігрова логіка покрита тестами, і вони не піднімають ні сервер, ні сокети
- [ ] кубик можна «підмінити» в тестах (детермінований random)

Питання собі:

- Чому кубик кидає сервер, а не телефон?
- Що простіше тестувати — логіку всередині обробника сокета чи окрему чисту функцію? Чому?

## Етап 5 — Postgres, Drizzle, журнал подій

**Вчу:** Drizzle ORM, міграції, зв'язки, транзакції, event sourcing.

- Таблиці: `games`, `players`, `game_events` (кожна дія в грі — рядок)
- Стан гри можна відновити, програвши всі події з початку (реплей)
- Сервер перезапустився посеред гри → гра продовжується з БД

Готово, коли…

- [ ] Postgres піднімається через `docker-compose`
- [ ] міграції — через Drizzle, схема в коді
- [ ] після рестарту сервера незакінчена гра відновлюється
- [ ] є реплей: екран може «прокрутити» завершену партію хід за ходом

Питання собі:

- Зберігати поточний стан чи список подій? Які плюси й мінуси в кожного?
- Навіщо тут транзакції? Що зламається без них?
- Чим Drizzle відчувається інакше, ніж Prisma з chapter_4?

## Етап 6 — Перша мініігра

**Вчу:** таймінги, latency, чесність у realtime.

- Наприклад «хто швидше натисне»: екран показує сигнал, гравці тиснуть на телефонах
- Сервер визначає переможця і нараховує монети

Готово, коли…

- [ ] мініігра запускається з машини станів і повертає результат у гру
- [ ] натиснув до сигналу → фальстарт
- [ ] результат справедливий навіть для гравця з повільнішим інтернетом (або свідомо вирішив, що ні,
      і записав чому)

Питання собі:

- Чий час правильний — телефону чи сервера? Як виміряти затримку до кожного гравця?

## Етап 7 — Статистика і лідерборди (SQL глибше)

**Вчу:** агрегації, `GROUP BY`, віконні функції, індекси, `EXPLAIN ANALYZE`.

- Профіль гравця: скільки ігор, перемог, середнє місце, улюблена клітинка
- Лідерборд: топ гравців за різними метриками
- Нагенерувати 100k+ фейкових подій і подивитися, що стане повільним

Готово, коли…

- [ ] хоча б один запит з віконною функцією (`RANK()`, `ROW_NUMBER()` тощо)
- [ ] знайшов повільний запит через `EXPLAIN ANALYZE` і пришвидшив індексом
- [ ] розумію, коли Drizzle query builder, а коли сирий SQL

Питання собі:

- Чому індекс пришвидшує читання, але сповільнює запис?

## Етап 8 — Redis і кілька інстансів сервера

**Вчу:** Redis, pub/sub, горизонтальне масштабування WebSocket-серверів.

- Стан активних кімнат — у Redis, а не в пам'яті процесу
- Запустити 2 інстанси сервера: гравці на різних інстансах у тій самій кімнаті бачать одне одного

Готово, коли…

- [ ] 2 інстанси сервера + Redis у `docker-compose`, гра працює між ними
- [ ] вбив один інстанс → гравці перепідключаються на інший і гра триває

Питання собі:

- Чому WebSocket-сервер важче масштабувати, ніж звичайний REST API?
